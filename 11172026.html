Executive summary

1

Two confirmed supply-chain breaches in one day, both through trusted third parties — and Google says agentic attacks have crossed a threshold. Barracuda confirmed on 16 November that an attacker used a cloud access key it had issued to a third-party AI company and never retired — the key sat in a configuration file in the vendor’s GitHub repository — to enter about 10 cloud accounts over 44 hours on 1–2 November, in an intrusion matching the ARTEX pattern. Infoblox confirmed the same day that attackers used a data-migration vendor’s trusted access to exfiltrate customer NIOS configuration data and employee records, including Social Security numbers, from its SharePoint. Google’s AI Threat Tracker, published overnight, says adversarial AI has reached a “critical inflection point”: agentic frameworks are now used in live intrusions, and Mandiant responded to LLMJacking incidents in 2026 affecting financial services firms, with single-day fraudulent charges over $100,000 and worst cases reaching $1 million. The Barracuda failure was a key-lifecycle failure, not an AI-framework failure: a key issued for a retired project stayed live. The Infoblox “products not involved” line does not cover the data already taken: customer network-identity configuration in attacker hands is follow-on attack material.

2

Patching moves: N-able Hotfix 3 has shipped, Apache Axis exploitation is confirmed against two products, and ScreenConnect was exploited against MSP technicians. N-able released Hotfix 3 on 16 November for the 4EverAble2Shell / Agent2Shell chains and has permanently blocked the Legacy API; hosted upgrades are complete and on-premises general availability is open. Rapid7 confirms Apache Axis CVE-2026-90436 (9.8, unauthenticated remote code execution) was exploited against Atlassian Confluence Data Center on 13 November as well as against N-central, and Huntback counted 21 N-central servers mining XMRig, 19 of them already on Hotfix 2. Huntress confirms ScreenConnect CVE-2026-84869 (9.9) was exploited against MSP technicians: a guest session compromised a technician workstation in about nine seconds on 12 November, and more than 688,000 guest “run file” requests were sprayed across 42 MSP servers between 20 October and 16 November. The ScreenConnect fix sits on the technician client, not the server — patching the server alone leaves the hole open — and Hotfix 2 was not sufficient protection for N-central, so HF3 should not wait for a maintenance window.

3

Korea: the FSI special audit has begun, KOMSCO confirms 3,083 customers affected, and Coinone took about 70 hours to disclose — while N0n’s leak-site claims now name Visa, Mastercard and JPMorgan Chase. The Financial Services Commission opened its special audit of the breached Financial Security Institute on 16 November; the FSI’s evaluation system is still shut down with no recovery date. Unknown actor — Barracuda cloud breach, ARTEX pattern

Security vendor; cloud accounts, source-code repositories and Kubernetes clusters

TTPs
No MITRE mapping published for the Barracuda incident itself. Barracuda says the intrusion used machine-style labels, probing methods and hunting routines matching ARTEX; the FBI FLASH-20261113-001 mapping for ARTEX was published on 13 November and is the standing reference, carried in the 16 November edition — it is not a new sighting in this edition.
Impact
Confirmed (Barracuda Trust Center advisory, 10 Nov, updated 13 Nov; BleepingComputer, 16 Nov). An attacker used a cloud access key Barracuda had issued to a third-party AI company for an earlier project and never retired. The key was stored in a configuration file in the vendor’s GitHub repository and was apparently stolen when the vendor’s development environment was compromised in October. The attacker entered about 10 of Barracuda’s cloud accounts over a 44-hour period on 1–2 November, moving through a data-analytics environment, source-code repositories and Kubernetes clusters; a second attempt to create a new cloud administrator identity was blocked. The intrusion was discovered on 4 November, when an engineer noticed odd activity on their own account. Barracuda says the attack was financially motivated and used machine-style labels, probing methods and hunting routines matching ARTEX. Barracuda says it found no direct evidence that XDR customer integration credentials were viewed, but has told some customers to reissue them as a precaution. The control failure was key lifecycle: a retired project’s key stayed live and sat in a vendor’s public-facing code repository. The ARTEX attribution is pattern-matching, not a named actor, and Barracuda has not said which AI company held the key. Any key issued to a third party for a finished project is live exposure.

That line is narrow: customer network-identity configuration in attacker hands is direct follow-on attack material against those customers’ networks. The vendor is unnamed, so customers cannot check their own exposure to it; firms using Infoblox should watch for a direct notification and review third-party access to their own collaboration systems.

Unknown actor — ScreenConnect CVE-2026-84869 exploited against MSP technicians

Managed service providers and their clients, including financial firms; technician workstations

TTPs
No MITRE mapping published in the Huntress post. A guest in a ScreenConnect session triggers file transfers the technician’s host client runs without authorisation.
Impact
Confirmed exploitation analysis (Huntress, 16 Nov). A guest in a ScreenConnect session can trigger file transfers the technician’s host client runs without authorisation (CVE-2026-84869, CVSS 9.9; disclosed by ConnectWise on 8 September, fixed in host client 26.6.5+, in CISA KEV since 11 September). Huntress confirms a full technician-workstation compromise in about nine seconds on 12 November: a guest-pushed update_224ac089.bat decoded a Telegram bot token, downloaded masterdarky[.]com/WindowsUpdate.msi and installed a rebranded ScreenConnect client. Across 42 MSP ScreenConnect servers, from 20 October to 16 November, there were more than 688,000 guest “run file” requests for update.bat / update_<8 hex>.bat from 29 IP addresses; three servers were still being sprayed on 16 November. A canary marker.txt push on 13 November proved the exploit against a second technician. This is distinct from the 14 November fake “Binance” / “KuCoin” guest-session trap campaign, in which no exploitation was seen. The fix sits on the technician client, not the server — patching the server alone leaves the hole open — and the lure theme used crypto-exchange names, so a technician compromise can cascade to every client the MSP serves. Indicators are in the Indicators section.

Barracuda — intrusion via an unretired vendor key (NEW)

Barracuda confirmed on 16 November that an attacker entered about 10 of its cloud accounts over 44 hours on 1–2 November using a cloud access key it had issued to a third-party AI company for an earlier project and never retired. The key was stored in a configuration file in the vendor’s GitHub repository and was apparently stolen when the vendor’s development environment was compromised in October. The attacker moved through a data-analytics environment, source-code repositories and Kubernetes clusters; a second attempt to create a new cloud administrator identity was blocked. Barracuda found no direct evidence that XDR customer integration credentials were viewed, but has told some customers to reissue them as a precaution.

The failure was key lifecycle with an AI-vendor wrapper, not an AI attack: the key should have died with the project. Firms should audit every key issued to a third party for finished work, and check their own GitHub repositories and config files for live credentials, because that is where this key was sitting.

Infoblox — breach via a SharePoint migration vendor (NEW)

Infoblox confirmed on 16 November that attackers used a compromised third-party data-migration vendor’s trusted access to exfiltrate data from its Microsoft SharePoint. AI in the current threat landscape

The three AI roles are kept separate. Vendor forecasts are marked as forecasts.

AI as a target

Google Threat Intelligence Group — LLMJacking hit financial services (16 Nov). GTIG’s AI Threat Tracker, published 16 November at 18:30 UTC (17 Nov 02:30 SGT), says Mandiant responded to several LLMJacking incidents in 2026: financially motivated actors hijacking cloud and LLM credentials and quotas, with single-day fraudulent charges over $100,000 and worst cases reaching $1 million. The November LLMJacking write-up covers intrusions affecting financial services, retail, transportation and technology organisations in North America, South America and Asia-Pacific, including abuse of LiteLLM CVE-2026-40217 to escalate virtual keys to admin. GTIG also tracks “LLM Mixers” reselling stolen LLM access at $0.10–$25 per million tokens.

Barracuda — the target was an AI vendor’s development environment (16 Nov). The key used in the Barracuda intrusion was stolen when a third-party AI company’s development environment was compromised in October; the key then sat in a configuration file in the vendor’s GitHub repository. The AI vendor is unnamed.

LLMJacking is now a confirmed financial-services problem, not a hypothetical — the charges are the measurable damage, and the LiteLLM flaw in the watchlist is the same product class being harvested in practice. Banks self-hosting AI gateways or inference endpoints should treat them as internet-facing credential stores, not internal tools, and should rotate any key that was ever exposed. The “LLM Mixer” market means a stolen key is monetised quickly, so detection time matters more than the key’s nominal value.

AI as a weapon or accelerator

GTIG AI Threat Tracker — agentic attacks cross a threshold (16 Nov). Google’s quarterly tracker says adversarial AI has reached a “critical inflection point”: actors have moved beyond manual prompting to autonomous multi-agent frameworks in live intrusions. Confirmed or observed in the wild: ARTEX, CAIRN (against US aerospace targets), CyberStrikeAI and PentAGI (a customised PentAGI used from late August to early October 2026 for reconnaissance and scanning across Asia), with experimentation on HexStrike AI. For the first time, GTIG reports a fully automated vulnerability-discovery-to-exploitation pipeline — a framework it calls exploit_agent, found on an exposed staging server, which diffs patches, drafts exploits and executes them with no human in the loop (Russian-language configuration comments; victim telemetry suggested interest in French media / entertainment and education sites). GTIG gives no success rate or victim count — do not present one. Supporting speed evidence: LLM-built working exploits for chained PaperCut zero-days CVE-2026-81578 / CVE-2026-82078 within a day of disclosure in late August, and a GreyNoise-reported widespread campaign four days later assessed as likely LLM-built; zero-day exploits spiked to 22 in August 2026 against an 11-per-month 2026 average. ExtraHop separately counted 3,447 ARTEX hosts on 16 November (reported via CyberPress).

Unit 42 — China-nexus CL-STA-1238 used Cairn to breach 10 organisations (16 Nov, via Dark Reading). China-nexus actors ran 25 operations in August–September against at least 19 organisations, achieving unauthorised access or data retrieval at 10. Seven targets were semiconductor / advanced-manufacturing supply chain, three US defence / defence-policy, plus human-rights and civil-society groups. Impact included dozens of valid credentials, more than 1 million records exposed at one organisation, military and government identities retrieved, persistent admin accounts created, and a live industry standards-ballot document modified. Cairn (model-agnostic; here driven by Zhipu GLM 5.2 and DeepSeek V4 Flash / Pro) planned, executed and recorded operations autonomously from a target and a goal. Initial access ran through known weaknesses — authentication bypasses, IDOR, mass-assignment privilege escalation, weak or default credentials, exposed cloud APIs and dated public CVEs. No BFSI victims were named.

Suspected DPRK cluster MIDNIGHT NEPTUNE targeted crypto organisations (GTIG, 16 Nov — suspected, not proven). GTIG reports a suspected DPRK cluster targeted cryptocurrency organisations in North America and Europe via fake-recruiter personas (SynthID-watermarked imagery) and ClickFix lures, then modified .claude/settings.json in internal repositories so launching Claude Code downloaded the SOMBERMEME backdoor, masking movement with GitHub personal access tokens named after Microsoft Copilot.

KOMSCO “AI-used attack” and Autopay “LLM-assisted attack” — company characterisations only. Segye reports KOMSCO characterised the chak breach as an “AI-used attack, similar in pattern to recent financial hacks”, with no technical evidence published. Autopay’s security manager described its attack as highly automated and likely LLM-assisted, with no malware or phishing — again with no technical evidence published. Neither is presented here as a confirmed AI-driven attack.

No new AI-scaled phishing, vishing or deepfake campaign against a named bank was found in this window.

AI as a risk and control problem for BFSI

CrowdStrike — backdoored LoRA models are a supply-chain risk (16 Nov; lab research, not in-the-wild exploitation). CrowdStrike’s Cyber Superintelligence Lab built on ProjectDiscovery’s October 2026 proof of concept (a roughly $50 LoRA fine-tune of Qwen2.5-7B trained to emit a tool call to an attacker URL on a trigger phrase) and built a two-stage pre-deployment defence: static weight analysis to flag undisclosed merged LoRAs, then trigger recovery to confirm the backdoor and recover the activating input. Across 16 lab models (8 backdoored, 8 benign), the scanner flagged all 8 backdoored models and Stage 2 confirmed a trigger in every one — covering tool-call hijacking, injectable shell code, typosquatted imports (for example pandas2) and refusal-flips — and cleared the 2 benign models escalated from Stage 1. A side finding: fine-tuning alone can erode refusal behaviour (“alignment erosion”). Limits stated: 16 models is a test, not a population; full fine-tunes and direct weight edits are not addressed. CrowdStrike states no in-the-wild exploitation is reported.

Barracuda key lifecycle is a governance failure, not a model failure. The key that let an attacker into Barracuda’s cloud was issued to a third-party AI company for an earlier project and never retired, then stored in a configuration file in the vendor’s GitHub repository. The control problem is vendor-key inventory and retirement, plus scanning code repositories for live credentials — the same discipline the Cursor / Fireworks cascade demands.

Crédit Mutuel Arkéa — chairman’s AI claim is still uncorroborated. An aggregator piece dated 16 November (03:55 SGT 17 Nov, citing el-balad) repeats chairman Julien Carmona’s claim that advanced AI was very likely involved in the attack and that about €100m was drained via a third-party provider. No primary French source was found for the AI remark, and no supporting evidence was given. Do not present the AI claim as confirmed. The $108.8m Bitquery figure conflicts with the earlier estimate of more than $133m (ZachXBT) — do not merge the two figures.

GTIG’s “LLM Mixers” and the patch-to-exploit pipeline compress the control window. Stolen LLM access is resold at $0.10–$25 per million tokens, and a fully automated pipeline now diffs patches and drafts exploits with no human in the loop. For BFSI, the practical consequence is that the time between a patch landing and an exploit existing has shrunk to hours — patch windows and key-rotation windows need to match that speed, not a monthly cycle.
