The distinction that decides your response

A crash in a Node.js worker is easy, reliable and public. Code execution is neither. Everything in the PoC ecosystem that "works" mostly works by killing the process — and because failed exploitation attempts also crash workers, an attacker who cannot get a shell still has a denial-of-service primitive. Patch on the RCE claim's plausibility, not on its proof.

The exploitability contest — where it actually stands

Neither position has been refuted, and the honest reading is that they are now answering different questions.

  • For reachability: ELLIO re-demonstrated a shell on stock, unmodified Node.js 24.22.0 x86-64 against four targets (plain node:http, official node:24.22.0-slim as root, Express 5.3.0, Koa 3), default configuration, ASLR left on, at roughly attempt 5. That is broader than Imperva's arm64-only result.
  • For the dissent: Red Hat still states there is no public, reliable remote-code-execution proof of concept, and rates the issue Important at CVSS 8.1 with AC:High rather than Critical — citing ASLR, NX, FORTIFY and SELinux. That remains true: ELLIO and Imperva have both withheld exploit code.
  • What would settle it is released code that works on a default build without per-build tuning. Nobody has published that, and the only in-the-wild attempt did not work.

Detection and exposure

  • New rule packs. ionsec/node2shell-detector (created 26 Oct) ships 14 Sigma, 14 Suricata (SIDs 1006600–1006699), ModSecurity and 7 YARA rules, with a 25-entry fingerprint catalogue including the Content-Encoding: br request shapes. Blevene’s gist adds 8 Sigma rules and Suricata sid 2026114971 (inbound br token) plus an egress flowbits pair. Fortinet ships IPS DB 37.321; Rapid7 added an authenticated check in its 26 Oct content release.
  • Better behavioural signals than “crash then execution”. Misses mostly crash the worker, so look for bursts of Node.js segfaults/restarts right after large br bodies — and treat the resulting core dumps as a data-loss event, because with systemd-coredump they land in /var/lib/systemd/coredump and can contain other users’ session tokens. Note the failure mode differs by ecosystem: Python Brotli/brotlicffi, the PHP extension’s streaming API and the Ruby gem hang instead of crashing; PHP spins at 100% CPU.
  • Do not use process.versions.brotli as a patch check. It reads 1.2.0 on both patched and unpatched Node.js builds. Check the Node release version instead.
  • Exposure is still unmeasured. Akamai is quoted as finding 61% of networks on affected Node.js versions (the page returned 403 here — unexecuted, quote is second-hand); the Phoenix tracker reports ~80 products with 38 fixed, 12 in progress, 19 still vulnerable as of 26 Oct. No Shadowserver, Censys or Shodan count was obtainable.

What the flaw actually is

Read this before any of the exploitability argument, because the argument is entirely about whether this write is reachable.

Brotli's DecodeBlockTypeAndLength() must decide whether a malformed block switch is a fatal format error or a request for more input. It conflated the two: a fast path ignored the return value, so the streaming decoder treated an invalid block switch as "need more bytes" and kept appending into an eight-byte internal buffer. The overrun writes into adjacent decoder state.

The upstream fix is commit 0ed4268a — "Detect and report invalid stream earlier" — which introduces the distinct error BROTLI_DECODER_ERROR_FORMAT_BLOCK_SWITCH (-17). Related commits: 50a9b70, b418fa8, da98063.

The detail that matters most for inventory

The fix landed upstream in February 2026 and was not labelled a security fix. Disclosure followed eight months later, on 21 October, with the Node.js release. Anything that vendored, pinned or bundled a Brotli build between those dates is vulnerable regardless of when it was last "updated". A dependency manifest showing a recent build proves nothing; you have to know which Brotli that build contains.

Reported by OpenAI Codex Security — Khai Tran and Sylvie Mayer — and fixed by mcollina and aduh95. Tracked as CVE-2026-111497 / GHSA-9v8h-qqgm-4m35, CWE-787 with CWE-252 as the root cause. Nicknames in circulation: Node2Shell, HTTP2Shell, Broccoli2Shell, Python2Shell — the proliferation of names is itself a sign the blast radius is not Node.js.

The Python trap

You do not need to import Brotli to be exposed. requests, urllib3, aiohttp, httpx and Scrapy auto-decode Content-Encoding: br when either Brotli package is installed. Worse, earlier urllib3 guidance told users to require Brotli ≥1.2.0 or brotlicffi ≥1.2.0.0 — which are the last vulnerable releases. Extras such as urllib3[brotli], httpx[brotli] and aiohttp[speedups] pull them in on purpose.

Read the pattern, not just the list

Not one of JFrog’s four additional cases is a completed RCE. They are instruction-pointer control, native crashes, and an infinite loop. That is the third independent confirmation of the grading in this report: the primitive is real and reachable in far more places than Node, but the distance from the primitive to a shell is long, target-specific, and nobody has closed it outside Node.

What they do prove is reachability — and reachability is the whole inventory problem. A 534-byte Parquet page that hangs a worker is a denial-of-service a file upload can deliver, with no HTTP stack in the path at all.

The two questions, and the one mitigation that is widely misunderstood

JFrog’s framing is the right one to hand to an infrastructure team, because it splits one unanswerable question into two answerable ones:

  1. Is the vulnerable implementation present? Bundled, linked, or inherited transitively — not just declared.
  2. Can untrusted input reach the decoder? Through a request body, a fetched response, a media file, a Parquet page, a firmware image.

“Yes” to the first and “no” to the second is not an emergency. “Yes” to both is. Most inventories answer only the first, and a scanner match is evidence of presence, not proof of exploitability.

Correction: removing br from Accept-Encoding is not a fix

A widespread mitigation circulating is to stop advertising Brotli in Accept-Encoding. On the outbound path that is insufficient — an attacker-controlled server can return Content-Encoding: br regardless of what you asked for, and a client that trusts the header will decode it. You must refuse to decode Brotli responses from untrusted origins, not merely decline to request them. Treat any guidance that stops at Accept-Encoding as incomplete.

The useful corollary, from Aikido: in default configurations Apache and nginx do not decode Brotli, so neither is a vulnerable carrier at the edge. The exposure is in the application and its client libraries, which is where inventories usually stop looking.

How the rename has been received

The naming proliferation is being mocked, and the mockery is worth knowing about because it predicts how the issue will be deprioritised. The most-shared formulation: “Three days from now → #php2shell. Today → #http2shell. One week from now → #server2shell. One year from now → #human2shell.” Another calls it a cyber soap opera that “drowns devs in an avalanche of buzzwords”.

Both things are true. The name inflation is real and mildly absurd. But the sequence underneath it is a factual widening: each name was coined because someone demonstrated the decoder somewhere the previous name did not cover, and the last one came with four reproductions. The practical reading: ignore the marketing, act on the second question above — whether untrusted input reaches a vulnerable decoder in your estate, whatever the stack is called this week.

Attack paths

Three shapes. The inbound one is the one WAFs see; the outbound one they never will.

1 — Inbound: attacker sends the compressed body

  • Express 5 with body-parser 2.x — express.json() and raw() inflate Brotli by default (inflate: true). This is the widest exposure in the ecosystem.
  • Express 4 — not exposed this way; its body-parser returns 415 for br.
  • Koa family — @koa/bodyparser, koa-body, co-body; also Egg and Strapi.
  • Fastify with @fastify/compress.
  • Envoy / Istio with the Brotli decompressor enabled — the vulnerable code sits in the proxy, before your app.

A bare node:http server does not decode request bodies on its own. Express and body-parser are routes into the decoder, not the source of the flaw — which is why patching the runtime beats patching the framework.

2 — Outbound: attacker sends the compressed response

Any service that fetches a user-supplied URL and auto-decompresses the reply is exposed: Node fetch()/undici/axios/got, and Python requests/urllib3/httpx/aiohttp/Scrapy. The relevant features are the ones that fetch arbitrary URLs by design — webhooks, link previews, URL imports, image proxies, OIDC discovery, crawlers, and browsing AI agents.

No WAF covers this path

Imperva states its rules cover inbound only. A server-side fetch() that pulls a hostile Brotli response is egress traffic your edge never inspects and never compressed on the way in. Teams that "added a WAF rule" and stopped there have covered roughly half the exposure — and the half that is easiest to weaponise, because the attacker controls the server answering the request.

3 — File-borne

Anything that decodes Brotli inside a container format: Parquet, JPEG XL, WOFF2 fonts, some PDF paths, archives, and firmware images. This is why the "we don't serve compressed HTTP" answer is insufficient.

How to read this. The two positive reports are not contradictory — they are on different architectures and both required repetition, which is what a heap-adjacent write under ASLR looks like. But neither released code, and both describe success as probabilistic. The sceptical position is not crankery: it correctly identifies that a crash is not a shell, and that some public demonstrations used harnesses that made success much easier.

What is not in dispute: the patched release rejects the input every time, returning 400 with ERR__ERROR_FORMAT_BLOCK_SWITCH. That is a clean, usable verification signal.

Two mechanical facts from ELLIO that decide your risk
  • Per-build offsets. Official Node builds are non-PIE, so code addresses are fixed; ASLR only randomises heap, stacks and arenas. An attacker measures the offset once per build and reuses it. Disabling ASLR is not a mitigation — a fixed layout can be measured once and exploited forever.
  • A restart supervisor helps the attacker. Each crash gives a fresh process with a predictable socket fd. With a supervisor looping, attempts are cheap; without one, the service simply stays down. Your resilience configuration is part of the attack surface.

Detection

There is no payload signature worth writing. The signals are version, crash, and process behaviour.

On a patched system, the trigger is visible

Patched builds answer malformed block switches with a specific error rather than silence:

BROTLI_DECODER_ERROR_FORMAT_BLOCK_SWITCH   (-17)
Node HTTP surface: 400 + ERR__ERROR_FORMAT_BLOCK_SWITCH

Hunting for -17 on patched hosts is the cleanest way to find someone probing you. On unpatched hosts it never fires — absence proves nothing there.

Crash to execution

  • Node.js process crash followed by in-place program execution in the same workload — Sysdig's managed runtime rule, and the single best behavioural detection for this bug, because exploitation requires a crash-and-retry cycle.
  • Shell or downloader spawned by a Node/Bun/Python worker — parent process is the discriminator, not the command. Same lesson as the PHP2Shell case.
  • Repeated worker restarts under a supervisor correlated with inbound compressed bodies — the attacker's retry loop, seen from your side.
  • Unexpected outbound fetch to a user-supplied host that returns Brotli — the outbound path, and the one that has no network signature at all.
  • SIGSEGV / SIGABRT / heap-corruption aborts in Node, Bun, Python or Envoy — and note that these are also the DoS.
Core dumps are a data-loss event

Crashes can produce core dumps containing live credentials from the process heap. Containers often lack a working core handler, which is luck rather than design. If you enable core dumps for debugging, you have created a credential-exposure path on a service that a remote attacker can crash at will.

Response order

  1. Inventories the runtime, not the manifest. Ask each service which Brotli it actually links. Vendored and statically-linked copies are the whole problem, and SCA tools miss them.
  2. Patch to Node 22.23.4 / 24.22.1 / 26.12.1, Bun 1.4.4, Brotli 1.0.10 / 1.1.1 / 1.2.1, and the Envoy/Istio levels above. There is no runtime workaround.
  3. Close the inbound path in middleware while you wait: express.json({ inflate: false }) returns 415 — note it also rejects gzip, so test first. Reject Content-Encoding: br on request bodies at the proxy or load balancer.
  4. Close the outbound path separately. Disable automatic response decompression on clients that fetch user-supplied URLs, or route those fetches through a proxy that refuses br. This is the step most teams will skip — and dropping br from Accept-Encoding does not achieve it, because a hostile server can send Content-Encoding: br anyway.
  5. Disable Envoy/Istio Brotli decompression if you run them — the decoder is in the proxy, upstream of any application control.
  6. Then hunt for -17 on patched hosts, crash-then-execute patterns, and worker restart loops correlated with compressed request bodies.

Node 18, 20, 23 and 25 will never be fixed. If you are on one of those lines, the only remediation is to move.

Four themes

  • Fatigue is the dominant register. A third critical RCE in a week, after PHP2Shell, produced open cynicism rather than alarm — comparisons to a “cyber soap opera”, jokes about which runtime is next, and administrators describing weekend triage. Fatigue is an operational risk: it is the mechanism by which a real finding gets under-prioritised.
  • The renaming to HTTP2Shell is substantive, not cosmetic. It reflects the realisation that the decoder sits in proxies and Python clients too. Several posts treat the rename as the moment the blast radius became clear.
  • The exploitability argument is being had in public, by people who know the code. The strongest sceptical post makes a narrow, checkable claim about reachability of the write and about weakened harnesses. That is a technical dispute, not noise, and it is reflected in the grading above.
  • Some organisations have already withdrawn service. At least one open-data project suspended its API; a forum operator was publicly asked whether it had gone down over the vulnerability. Expect more precautionary downtime than confirmed incidents — which will inflate the apparent severity of the event in retrospect.
A caution on social sourcing

Several posts circulate a “9 detections, 8 IOCs” claim from a commercial intel page. The page itself advertises 31 indicators and 9 rules, all paywalled. The number in circulation does not match the source, and none of the values are visible. Do not carry counts you cannot inspect.

Method and limits

  • Passive only. No scanning, no exploitation, no contact with any listed host.
  • No dark-web collection. No Tor in this environment; substituted with abuse.ch (ThreatFox, URLhaus), OTX and public reporting, and labelled as substitution rather than coverage.
  • One source returned 403 (The Hacker News) and is recorded as unexecuted, not as a negative.
  • Two RCE claims are second-hand in detail. Neither Imperva nor ELLIO released exploit code, so reproducibility rests on their descriptions. We did not attempt reproduction — no vulnerable runtime was built here.
  • Version tables are from vendor and distributor advisories, consolidated from one detailed secondary source. Confirm the rows you act on against your own distributor.
  • The scanner observation is single-source and internally inconsistent on dates; treat it as a lead.
