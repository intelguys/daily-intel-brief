Java4Shell: CVE-2026-114938

Intelligence brief for SOC and vulnerability-management teams. A heap out-of-bounds write in OpenJDK’s AVX-512 Base64 decoder, disclosed on 17 November 2026 and patched the same day — demonstrated, by its discoverers, as unauthenticated remote code execution against default installs of Jira, Confluence, Jenkins, Keycloak, Artifactory and PingFederate. No exploitation in the wild has been reported. This page tracks the vulnerability, the patch rollout, and what independent labs have and have not reproduced.

Bottom line

  1. The bug is real, and the trigger is trivial. Sixty-four A characters followed by a single = make the HotSpot JVM’s hardware-accelerated Base64 decoder write 62 bytes past the end of a 50-byte heap array. The write happens before Java rejects the input as invalid. The discoverers turned it into a heap leak (“JavaBleed”) and then into remote code execution.
  2. RCE is demonstrated by the discoverers, not yet independently reproduced. Calif claims pre-authentication RCE against six widely deployed products in their default configurations; Wiz says it proved remote exploitation feasible against Jenkins, Confluence and Apache Tomcat. Other labs have reproduced the overflow, JVM crashes and a local heap disclosure — but not remote code execution. Oracle rates the flaw 8.1 (CVSS 3.1, high attack complexity); Calif rates it 9.2 (CVSS 4.0).
  3. Patching is under way but uneven. Oracle’s fixed builds shipped on 17 November, as did Amazon Corretto and Azul Zulu. Red Hat has shipped fixed builds for its Build of OpenJDK (portable and Windows), and all six RHEL errata shipped on 19 November; the Red Hat container images and the Red Hat Build of Keycloak remain affected. Eclipse Temurin has now published fixed binaries for all four lines on x64 Linux, Microsoft has shipped its fixed builds, and BellSoft has confirmed fixed CSPU builds (17.0.21.1, 21.0.13.1, 25.0.5.1, 27.0.1.1) that include the patch. Okta has published fixed versions for its Access Gateway and agents (19 November). Two JVM flags close the exposure where patching must wait — but one of them, -XX:UseAVX=2, stops OpenJDK from starting on ARM, so use -XX:-UseBASE64Intrinsics on mixed estates.
  4. The hard part is inventory, not the patch. The flaw is in the Java runtime, not in any application or library, so dependency scans will not find it — and runtimes bundled inside third-party products, container images and appliances may not appear in software inventories at all. Three conditions must all hold: an OpenJDK build from 17.0.6 onward, an x86-64 processor with AVX-512 VBMI, and an application that decodes attacker-controlled Base64.

At a glance

Java4Shell in brief

A memory-corruption flaw in the Java runtime itself, disclosed and patched on 17 November 2026. This section is a summary only — every figure here is stated in full, with its caveats, in the sections below.

  • The flaw. CVE-2026-114938, a heap out-of-bounds write in HotSpot’s x86-64 Base64 decode intrinsic — hand-written assembly that uses AVX-512 VBMI instructions to decode Base64 faster. A malformed input, 64 A characters followed by a single =, makes the decoder calculate a negative output length and write a full 64 bytes into a 50-byte array, 62 bytes past its end. On older OpenJDK 17 builds the trigger is 128 As instead. Java eventually rejects the input, but by then neighbouring heap objects may already be corrupted.
  • Scores disagree, and the disagreement is the story. Calif rates it 9.2 under CVSS 4.0 (critical); Oracle and the OpenJDK Vulnerability Group rate it 8.1 under CVSS 3.1 (high, attack complexity high, “difficult to exploit”); Red Hat gives 9.8 and now publishes its own vector (CVSS:3.0/AV:N/AC:L/PR:N/UI:N/S:U/C:H/I:H/A:H) — attack complexity low, against Oracle’s high, which is the whole disagreement. The CVSS 3.1 vector is published (AV:N/AC:H/PR:N/UI:N/S:U/C:H/I:H/A:H); no CVSS 4.0 vector has been published, and at least one secondary source attributes the 9.2 to South Korea’s National Cyber Security Center rather than to Calif.
  • Who is affected. Three conditions must all hold: an OpenJDK build from 17.0.6 onward (lines 17, 21, 25 and 27, plus Oracle’s Java 8 Enterprise Performance Pack build 8u511b33-perf), an x86-64 processor with AVX-512 VBMI (Intel Xeon Ice Lake through Granite Rapids; AMD EPYC and Ryzen Zen 4 and newer), and an application that hands attacker-controlled Base64 to java.util.Base64.Decoder. Standard Java 8 and 11 are not affected. ARM64 is not affected.
  • Exploitation, as of 22 November. Calif demonstrated pre-authentication RCE against six products in their default configurations and post-authentication RCE against five more, plus a client-side attack over TLS. Wiz proved remote exploitation feasible against Jenkins, Confluence and Apache Tomcat and built a PoC with its Atlas harness in two hours. Independent labs have reproduced the overflow, JVM crashes and a local heap disclosure — not remote code execution. No exploitation in the wild has been reported, and the flaw is not in CISA KEV.
  • The AI angle. Calif’s Quang Luong found the bug in about an hour using OpenAI’s Codex, auditing HotSpot’s JIT compiler, intrinsics and cryptography code, and had a first working exploit two hours later, for under $200 in AI token costs. OpenAI co-founder Greg Brockman credited GPT-6 Cyber and said the work was part of OpenAI’s Patch the Planet initiative. The New York Times independently verified the vulnerability using proof-of-concept details supplied by Calif.
  • Same researchers, second runtime. Calif disclosed PHP2Shell first — its write-up opens “After we disclosed PHP2Shell, we realized many people didn’t know what PHP was. So we decided to go after something a little more familiar: Java.” The firm also found Squidbleed, an older Heartbleed cousin in the Squid proxy, earlier in 2026.

The vulnerability

What the bug is

Base64 is how binary data is commonly represented as text — in authentication protocols, file uploads and network messages. To decode it faster, OpenJDK’s HotSpot JVM substitutes hand-written assembly for the Java decoding loop once a method runs hot. The x86-64 Base64 intrinsic processes input in 256-byte blocks (64-byte blocks below that), using AVX-512 VBMI instructions, and handles the final few characters — the padded tail — in a separate code path. That path is where the bug lives.

For the 65-character input above, OpenJDK allocates a 50-byte result array: the decoded length is calculated as (ceil(input_length / 4) * 3) - padding. After decoding the first 64 characters, the routine mishandles the stray = and calculates a negative output length. Calif’s pseudocode of the faulty logic:

output_len := (input_length / 4) * 3
// handle padding
if input[input_length - 1] == '=':
    output_len -= 1
    input_mask >>= 1
    if input[input_length - 2] == '=':
        output_len -= 1
        input_mask >>= 1
output_mask := bzhiq(-1, output_len)

When the remaining input is of the form =, ==, X=, X==, XY= or ===, output_len is computed as zero and then decremented, underflowing to -1 or -2. Because bzhiq(-1, output_len) does not change any bits when output_len >= 64, the result is output_mask == -1u64 — all 64 bits set. The following evmovdqub (masked vector store) therefore writes all 64 bytes, starting at offset 48 of the 50-byte array: 62 bytes past its end (63 for a == tail). The generated stub returns early when it detects invalid input, and the Java code then throws IllegalArgumentException — but the write has already happened.

The write itself is almost entirely fixed: the attacker fully controls byte 0, partly controls byte 1 (4 bits), and bytes 48–63 are always 0x9a. Only the landing position is controllable. Calif’s exploitation strategy turns that fixed write into control by overwriting a buffer’s length — a classic JavaScript-engine primitive. The length-corrupted buffer becomes the writer: it keeps accepting chosen bytes, so a neighbouring array or object can be corrupted with chosen values. Corrupting a second array’s length, and having its data copied back into the response, builds the reader — a heap-disclosure primitive Calif calls JavaBleed, able to leak heap contents that may hold PII, private keys, other secret keys and tokens. From writer and reader, the chain repairs the objects the linear write damaged, mounts data-only attacks on application logic, and escalates the bounded write into arbitrary writes reaching the JVM’s code cache and hooks for code execution.

Getting there needs heap grooming. G1 divides the heap into fixed-size regions, and HotSpot normally gives each thread a private thread-local allocation buffer (TLAB), so objects created by different request threads have no useful order. Calif sprays several live writer/reader pairs, controls the allocation route (array size and remaining TLAB space decide whether HotSpot refills the TLAB or takes the attacker-preferred outside-TLAB path), and paces requests so each chunk is TCP-acknowledged before the next is sent, giving control over allocations up to the critical point. The attack is sensitive to network conditions — low, stable round-trip times are preferred — and Calif rented a VM in the same region as its target rather than tuning TCP/IP settings. The chain runs in stages: warm (valid decodes until the JIT selects the affected fast path), rehearse (an optional safe round for calibration), trigger (the malformed tail), disclose (enlarge the reader, collect response-derived heap bytes), repair (restore temporary headers and untouched neighbours), finish (make the application-specific change and verify it through a live request). A misplaced trigger can crash the JVM, but in many cases the attack can simply be retried.

Two limitations bound the attack. Some grooming profiles need partial request bodies to reach the application, and a proxy that buffers the complete body removes their release timing — nginx buffers request bodies by default — though that is not a general mitigation: Elasticsearch runs from one complete request, and after a WebSocket upgrade later frames pass through a tunnel where buffering no longer applies. And there is no universal payload: each chain needs a decoder route, a live writer, a returned reader or another feedback path, a heap layout and an application action.

Provenance of the code. The AVX-512 Base64 optimisation was written as JDK-8268276 for JDK 18 and backported to Java 17 as JDK-8296735 in the 17.0.6 update — which is why 17.0.6 is the boundary and why the vulnerable code has been shipping since January 2023. Endor Labs describes the fix as four lines. The trigger, in full:

AAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAA=

On older OpenJDK 17 builds the trigger is 128 A characters followed by =.

Exploit availability

What exploit code exists, and what is withheld

Calif’s safe trigger. Calif published a self-contained proof of concept in its write-up. It warms the Base64 decoder until the vulnerable intrinsic is used, then decodes the malformed 64 × “A” + “=” input into a 4096-byte array. On an affected JDK it prints REPRODUCED: the decoder rejects the input, but 62 bytes (offsets 50 to 111) past the decoded output have already been overwritten. Every write lands inside a real array, so the trigger is safe to run. The product-specific exploits — the weaponised chains for individual products — stay private until everyone has had a chance to upgrade; Calif says it will publish them later.

GitHub. cve.now counts 55 proofs of concept on GitHub as of 18 November, the first appearing on 18 November at 02:15 UTC (Ghost-Bx1/java-exploits, r3dvei1/java4shell). Detection and hunting

Hunt the effect, not the request

No network indicators have been published. There are no IPs, domains, file hashes or malware families tied to Java4Shell exploitation, because no exploitation in the wild has been reported. Do not import indicators from unrelated Java or OpenJDK incidents. What exists to hunt on is behaviour:

  • JVM crashes. Unexpected JVM restarts and crash logs, especially SIGSEGV in the G1 collector — the failure mode Harness reproduced with small fixed TLABs, and the mode Blackpoint reproduced with repeated unauthenticated HTTP requests. CISA’s alert tells defenders to monitor for unexpected JVM crashes, rogue runtimes and suspicious Java processes. A JVM crash on an Ice Lake-class server with no obvious cause should now get a security review, not just a quick restart.
  • The trigger string. The 65-byte input — 64 As followed by = — is distinctive in request logs, WAF logs and authentication logs. It is a crash reproducer, not proof of exploitation, but it is the earliest observable signal of probing.
  • Heap-corruption symptoms. Neighbouring-object corruption can surface as wrong data in responses, corrupted tokens, or application logic behaving as if its inputs changed — the data-only attacks Calif describes. JavaBleed-style disclosure would surface as heap contents (PII, keys, tokens) appearing where they should not.
  • Exposure inventory. The CPU-flag check above establishes whether a host can run the vulnerable path; the runtime checker from Harness compares installed JDKs against the affected builds. WAF rules can help against some exploits as they emerge, but Wiz warns they are unlikely to cover all paths — the vulnerable code sits behind any endpoint that decodes Base64, including home-grown applications — and will never cover them completely.
  • Ready-made detection rules. The ikow toolkit ships six Suricata/Snort rules (exact trigger patterns, malformed Base64 padding, warm-up rate, hs_err crash indicator, JWT bearer pattern), five Sigma rules and six ModSecurity rules — the first Suricata and Sigma content for this CVE seen in this window. They are signature-based on the trigger shape, so they catch probing, not confirmed exploitation.
  • Tested WAF rules and an error signature. IONIX Research Labs published interim WAF rules tested on Cloudflare, AWS WAF and Akamai — a partial mitigation with documented gaps, not a replacement for patching. CrowdSec published a free virtual-patch AppSec rule (crowdsecurity/vpatch-CVE-2026-114938, 18 November; blog updated 19 November) that blocks the malformed Base64 trigger in authorisation headers, cookies and the parameters public exploits use — a stopgap, not a fix, covering only the places the WAF inspects. Microsoft published custom Azure WAF rules (18 November) for Azure Front Door and Application Gateway — Java4ShellB64Header, Java4ShellB64BodyField, Java4ShellB64Query and Java4ShellB64Authorization — matching long Base64 strings in headers, POST body fields, the query string and the Authorization header; again a stopgap, not a fix, and Microsoft says patching remains the primary remediation. A spike of IllegalArgumentException (“Input byte array has wrong 4-byte ending unit”) from java.util.Base64 on unauthenticated endpoints is a hunt marker for probing; ordinary malformed input causes the same errors, so it is a lead, not proof.

Action plan

What to do now

  1. Inventory the runtime, not the application. Review software inventories for JDKs and Java runtimes, including those bundled with third-party applications or included in container images and appliances. CISA warns these may not appear as separate entries in software inventories, and Sonatype notes that project dependency scans will not identify every affected installation — the flaw is in the runtime, not a library. Check the version each running service reports, not just what the package manager says.
  2. Patch the runtime; patching the application does not fix it. Install your vendor’s fixed build from the table above and restart the JVMs. Prioritise internet-facing systems first (CISA). Oracle’s fixed builds are 17.0.21.1, 21.0.13.1, 25.0.5.1, 27.0.1.1 and 8u513-perf; Corretto, Azul, Microsoft and Temurin (x64 Linux) have shipped, Red Hat has shipped fixed builds for its Build of OpenJDK and all six RHEL errata, BellSoft has confirmed fixed CSPU builds, and Okta has published fixed agent versions; the Red Hat container images and the Red Hat Build of Keycloak remain affected — track that vendor’s advisory rather than waiting for a generic alert.
  3. Where patching must wait, disable the intrinsic. Start the JVM with -XX:-UseBASE64Intrinsics to turn off the hardware-accelerated Base64 routines and fall back to the software decoder. This is the recommended flag: it works on every architecture. The alternative, -XX:UseAVX=2, disables AVX-512 — but OpenJDK on ARM does not recognise it and will fail to start, so applying it blindly across a mixed estate will crash ARM hosts. Apply -XX:UseAVX=2 only on x86-64 hosts. Both flags may carry a performance cost.
  4. Compensating controls. Where immediate patching is not feasible, CISA recommends restricting and validating Base64 input at the application boundary, enforcing input-size limits, and limiting unauthenticated access. Wiz recommends temporarily restricting external network access to vulnerable management portals (Jira, Jenkins, Keycloak) until mitigations or updates are deployed.
  5. Do not rely on the network edge. WAF rules and request-body buffering (nginx buffers bodies by default) blunt some attack profiles, not all: Elasticsearch runs from one complete request, and WebSocket frames pass through a tunnel after upgrade. Treat edge controls as delay, not defence.

No bank has been named as a victim, and no financial-sector alert has been issued. That is the whole of the victim record so far, and it should stay that way unless a named institution discloses. The relevance is structural, not incident-driven — and it is large.

Java runs the sector. Calif puts it bluntly in its write-up: Java powers 90% of Fortune 500 companies, and “banking, aviation, telecommunications, nearly every critical sector runs on Java, including national security systems.” Core banking systems, payment switches, trading platforms, messaging and event-streaming backbones (Kafka is on Calif’s post-authentication list) and the identity layer all commonly run on the JVM. Two of the six products Calif says it took over without logging in are identity systems — Keycloak and PingFederate — the single sign-on that guards staff access to everything else. Jenkins, Jira and Confluence are standard tooling inside financial IT. A runtime flaw needs no vulnerable application: any Java service that decodes attacker-controlled Base64 on affected hardware is a candidate, and Base64 is how authentication tokens, file uploads and network messages are commonly represented.

The practical exposure for a bank is the same inventory trap CISA describes, sharpened by the sector’s vendor estate: Java runtimes bundled inside third-party products, core-banking appliances and container images, on patch cycles the bank does not control, with the vendor’s fixed build as the only route. Red Hat’s bulletin naming Azure D-series instance families shows the exposure extends into cloud estates banks rent rather than own. Patch the runtime you run, chase the runtime your vendors run, and treat the two JVM flags as the bridge where a vendor’s build has not shipped — Red Hat’s remaining RHEL packages are the ones that matter most on 19 November, now that its Build of OpenJDK, Temurin (x64 Linux) and Microsoft have shipped.

Covered in the daily brief of 18 November 2026 (11182026.html) as the edition’s lead vulnerability; this page is the deep-research record for it.

Exposure

How much Java is actually out there

Unknown, and that is the honest answer. No vendor or sensor operator has published a count of internet-facing hosts running a vulnerable OpenJDK build on AVX-512 VBMI hardware, and none is quoted here. What is known:

  • Java is the world’s third most popular programming language (TIOBE, cited by Calif) and powers 90% of Fortune 500 companies (IBM, cited by Calif).
  • The vulnerable code has shipped in every OpenJDK build from 17.0.6 onward — since January 2023 — across all major distributions: Oracle, Corretto, Temurin, Microsoft, Azul, BellSoft, SAP and Red Hat.
  • The hardware condition is now common in cloud estates: Intel Xeon Ice Lake through Granite Rapids and AMD EPYC/Ryzen Zen 4 and newer. Red Hat names Azure Dsv5, Dsv6, Dasv6 and Dasv7 families as most likely affected.
  • The vulnerable path is chosen automatically on capable CPUs. No configuration is needed to be exposed, and no configuration short of the JVM flags or the patch removes the exposure.

Exposure is therefore best measured per estate — how many of your JVMs run 17.0.6 or later on AVX-512 VBMI hardware, including the ones inside vendor products — rather than from any global count. If a global count appears, it belongs here with its methodology, not as a bare number.

Lessons learnt

What this case shows so far

Two days in, the record already returns a short list. Each lesson below is drawn from the record above; where the record is still open, it stays open here.

The runtime is the blast radius, not the application

Nothing in Jira, Jenkins or Keycloak was at fault. The flaw sits in the Java runtime every one of them shares, which is why a single bug credibly threatens six unrelated products at once — and why patching the application cannot fix it. Inventory and patch the runtime; the application list is a triage aid, not the fix.

AI has compressed discovery-to-exploit to hours

One researcher, one hour to find the bug, two more to a first working exploit, under $200 in token costs; a second firm’s harness built a PoC in two hours before the details were public. The patch window is no longer measured against human exploit development. The same compression applies to defenders only if their inventory already knows which JVMs they run.

Score disagreement is a signal, not noise

9.2, 8.1 and 9.8 describe the same flaw. The gap is not arithmetic — it is a disagreement about exploitability, between a researcher who built the chain and a vendor that calls it difficult. Read the scorer and the attack-complexity judgement, not the number; and note when a score’s source is unnamed and its vector unpublished.

Bundled runtimes are the inventory gap

CISA’s warning is the operational core of this case: runtimes inside third-party products, containers and appliances may not appear in software inventories, and dependency scans cannot see a runtime flaw at all. The estate you can list is not the estate you run.

“No universal exploit” cuts both ways

Calif’s caveat is genuine — each target needs its own chain — but it is not reassurance. It means there is no single signature to detect and no single patch to the application layer; it also means a motivated adversary can tailor the chain per target, with AI, for the products that matter most. The absence of a generic exploit is not the absence of risk.

Withheld exploits buy time only if patching uses it

Calif is holding its product chains back until users have had a chance to upgrade, and other labs have so far reproduced crashes rather than shells. That window is measured in days: probing has already begun, GitHub PoCs are appearing, and a second firm says it has built its own working exploit. The value of the delay is spent on patching, not on reassurance.
